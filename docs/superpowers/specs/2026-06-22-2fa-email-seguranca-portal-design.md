# Design — 2FA por e-mail + reforços de segurança do portal

**Data:** 2026-06-22
**Status:** Aprovado (aguardando revisão final do spec)
**Abordagem escolhida:** A — incremental sobre o JWT atual

---

## 1. Problema e objetivo

O portal conterá informações de pagamento (`financials`) e documentos sensíveis
(`documents`, `contracts`). Hoje a autenticação é apenas e-mail + senha, com falhas
conhecidas:

- `JWT_SECRET` com fallback fixo no código (`'super-secret-key-unimed-mvp'`) —
  permite forjar tokens válidos para qualquer um que veja o repositório.
- Token JWT guardado no `localStorage` — exposto a XSS.
- Sem segundo fator, sem rate-limit e sem bloqueio por tentativas.
- Bloco de credenciais de teste (`senha123`) exposto na tela de login.

**Objetivo:** adicionar autenticação de duplo fator (2FA) por código de e-mail, no
padrão "dispositivo confiável" (estilo GitHub: o 2º fator só é exigido em dispositivo
novo), e corrigir os reforços de segurança adjacentes que tocam o mesmo código de login.

## 2. Decisões (confirmadas com o usuário)

| Decisão | Escolha |
|---|---|
| Método de 2º fator | Código por e-mail (OTP de 6 dígitos) |
| Padrão de UX | Dispositivo confiável (30 dias), 2FA só em dispositivo novo |
| Escopo | **Todos** os perfis (prestador, cooperado, admin, auditoria) |
| Reforços incluídos | Rate-limit + bloqueio, cookie `httpOnly`, tela de dispositivos, correção do `JWT_SECRET` |
| Envio de e-mail | API transacional **Resend** (abstraída atrás de `Mailer`) |
| Arquitetura | Abordagem A — incremental sobre o JWT existente |

## 3. Fluxo de login

### Dispositivo já confiável (caso comum)
1. Usuário envia e-mail + senha → backend valida com `bcrypt`.
2. Backend confere cookie `trusted_device` válido (não expirado, não revogado) →
   emite sessão direto. **Sem OTP.**

### Dispositivo novo (ou selo expirado)
1. Usuário envia e-mail + senha → `bcrypt` confere.
2. Backend **não** emite sessão. Gera OTP de 6 dígitos, salva o *hash* em
   `otp_codes` (validade 10 min, uso único) e envia por e-mail. Responde
   `{ needs_otp: true, challenge_id }`.
3. Frontend mostra a etapa "Digite o código enviado ao seu e-mail".
4. Usuário digita o código → backend confere hash, prazo e tentativas.
5. Se válido **e** marcou "confiar neste dispositivo": grava `trusted_devices` +
   cookie assinado (30 dias). Emite a sessão (cookie `httpOnly`).

### Regras transversais
- A senha é **sempre** exigida — o dispositivo confiável só dispensa o 2º fator.
- Reenvio de código: cooldown de 60s + limite por janela (máx. 5/hora).
- Cada falha de senha **ou** de OTP entra no `access_logs` e conta para o rate-limit.
- Falha de envio de e-mail retorna erro claro (não trava o usuário) e loga no servidor.

## 4. Modelo de dados

Migration `0009_2fa_email_otp.sql`. Tudo aditivo — não altera dados existentes.

```sql
CREATE TABLE IF NOT EXISTS otp_codes (
  id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id       bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  code_hash     text NOT NULL,            -- hash do código (bcrypt), nunca em texto puro
  purpose       text NOT NULL DEFAULT 'login_2fa',
  attempts      integer NOT NULL DEFAULT 0,
  consumed_at   timestamptz,              -- uso único
  expires_at    timestamptz NOT NULL,     -- now() + 10 min
  ip            text,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS otp_codes_user_idx ON otp_codes (user_id);
CREATE INDEX IF NOT EXISTS otp_codes_expires_idx ON otp_codes (expires_at);

CREATE TABLE IF NOT EXISTS trusted_devices (
  id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id       bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash    text NOT NULL,            -- hash do segredo do cookie, nunca o segredo cru
  label         text,                     -- ex.: "Chrome em Windows" (derivado do user-agent)
  last_ip       text,
  last_used_at  timestamptz NOT NULL DEFAULT now(),
  expires_at    timestamptz NOT NULL,     -- now() + 30 dias
  revoked_at    timestamptz,              -- revogação manual
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS trusted_devices_user_idx ON trusted_devices (user_id);
CREATE UNIQUE INDEX IF NOT EXISTS trusted_devices_token_uniq ON trusted_devices (token_hash);
```

**Princípios:** códigos e segredos de dispositivo nunca são guardados em texto puro
(só hash) — vazamento de banco não revela credenciais válidas. `otp_codes` é varrida
por limpa-expirados leve (na rota de login ou job simples).

## 5. Backend (`server.ts` + helpers)

### Endpoints
- **`POST /api/auth/login`** `{ email, password }` →
  - `bcrypt` falha → `access_logs` (falha) + rate-limit + `401` ("credenciais inválidas").
  - OK + cookie `trusted_device` válido → emite sessão, atualiza `last_used_at`. Retorna `{ user }`.
  - OK sem dispositivo confiável → gera OTP, envia e-mail, retorna `{ needs_otp: true, challenge_id }`.
- **`POST /api/auth/verify-otp`** `{ challenge_id, code, trust_device }` →
  - Confere expiração, `consumed_at`, `attempts`.
  - Código errado → `attempts++`, `access_logs` (falha), `401`. Estourou 5 tentativas → invalida o desafio.
  - Correto → marca `consumed_at`, `access_logs` (sucesso), atualiza `last_login_at`/`last_login_ip`.
    Se `trust_device` → cria `trusted_devices` + cookie assinado (30d). Emite sessão.
- **`POST /api/auth/resend-otp`** `{ challenge_id }` → cooldown 60s + limite por janela; novo código no mesmo desafio.
- **`POST /api/auth/logout`** → limpa o cookie de sessão no servidor.
- **`GET /api/auth/me`** → dados do usuário a partir do cookie (fonte única de verdade).
- **`GET /api/auth/trusted-devices`** (autenticado) → lista os dispositivos do próprio usuário.
- **`DELETE /api/auth/trusted-devices/:id`** → revoga (preenche `revoked_at`); só os próprios do usuário.

### Mudanças no middleware
- `authenticate` lê o JWT do **cookie `httpOnly`** (fallback ao header `Authorization`
  durante a transição, removido ao final).

### Helpers novos (arquivos pequenos e focados)
- `mailer.ts` — interface `Mailer` + `ResendMailer` + `ConsoleMailer` (dev).
- `otp.ts` — gerar/hashear/validar código, expiração, contagem de tentativas.
- `trustedDevice.ts` — emitir/conferir/revogar selo + cookie.
- `rateLimit.ts` — contagem de falhas recentes via `access_logs`.

## 6. Frontend

### `Login.tsx` — duas etapas no mesmo componente
1. **Etapa senha** (atual): e-mail + senha. Resposta `{ user }` → `/dashboard`;
   `{ needs_otp }` → etapa OTP.
2. **Etapa OTP** (nova): campo de 6 dígitos, e-mail mascarado ("s***@dominio.com"),
   checkbox **"Confiar neste dispositivo por 30 dias"**, botão "Reenviar código" com
   contador de cooldown (60s), link "Voltar". Sucesso → `/dashboard`; erro → mensagem inline.

### `api.ts` — transporte
- Token passa a vir em cookie `httpOnly`; o frontend **não lê mais** o JWT.
- Todas as chamadas usam `credentials: 'include'`.
- `localStorage` deixa de guardar o `token`. Dados do usuário vêm de `GET /api/auth/me`.
- Logout vira `POST /api/auth/logout`.

### Tela "Dispositivos confiáveis" (em configurações/perfil)
- Lista dispositivos (label, último acesso, IP, expira em) com botão **Revogar**.
- Opcional: "Revogar todos os outros".

### Remoção
- Apagar o bloco de credenciais de teste (`senha123`) das linhas ~156-166 de `Login.tsx`.

## 7. Reforços de segurança

### `JWT_SECRET` sem fallback
```ts
const JWT_SECRET = process.env.JWT_SECRET;
if (!JWT_SECRET) {
  console.error('FATAL: JWT_SECRET não definido. Abortando boot.');
  process.exit(1);
}
```
Garantir env var forte no Railway. Sem ela, o servidor não sobe.

### Cookie `httpOnly`
- `res.cookie('session', jwt, { httpOnly: true, secure: <prod>, sameSite: 'lax', maxAge: 24h })`.
- `secure: true` em produção (Railway é HTTPS); condicional por `NODE_ENV` em dev.
- `sameSite: 'lax'` mitiga CSRF; rotas que mutam estado são `POST`/`DELETE`.
- Dep nova: `cookie-parser`. `cors` passa a usar `credentials: true` + origem explícita.

### Rate-limit + bloqueio (`rateLimit.ts`)
- Por **IP** e por **e-mail/usuário**, contando falhas recentes no `access_logs`
  (resiste a restart e a múltiplas instâncias do Railway).
- Limites (ajustáveis): senha — 5 falhas / 15 min → bloqueio de 15 min; OTP — 5 erros
  no mesmo desafio invalida o código; reenvio — cooldown 60s, máx. 5/hora.
- Mensagem genérica para não revelar se o e-mail existe.

## 8. Envio de e-mail

```ts
export interface Mailer {
  sendOtp(to: string, code: string): Promise<void>;
}
```
- `ResendMailer` (dep nova: `resend`); config `RESEND_API_KEY`, `MAIL_FROM`.
- Em **dev local**, `ConsoleMailer` imprime o código no terminal (não envia e-mail
  real, não toca o Postgres de produção compartilhado).
- Em **produção**, ausência de `RESEND_API_KEY` → boot falha (mesma filosofia do `JWT_SECRET`).

**Conteúdo:** assunto "Seu código de acesso ao Portal Unimed: 123456"; corpo curto com
código, validade de 10 min e aviso "se não foi você, ignore". **Sem links clicáveis**
(reduz superfície de phishing).

**Pré-requisito de go-live:** verificar domínio de envio no Resend (SPF/DKIM). Até lá,
`ConsoleMailer` cobre dev/teste.

## 9. Casos de borda

- **E-mail não envia:** `login` retorna erro claro + log no servidor; usuário não trava.
- **OTP expirado/usado:** "código expirado, solicite um novo" + reenviar.
- **Vários códigos:** só o último vale; cooldown evita flood.
- **Selo expira no meio da sessão:** sessão ativa segue; próximo login pede OTP.
- **Usuário inativo / sem e-mail:** bloqueio na etapa senha; sem e-mail → erro de conta (admin corrige).
- **Revogar dispositivo durante sessão ativa:** sessão atual segue (JWT); efeito no próximo login (coerente com Abordagem A).
- **Relógio/timezone:** tudo em `timestamptz` com `now()` do Postgres.

## 10. Testes (meta 80%)

- **Unitários:** `otp.ts`, `trustedDevice.ts`, `rateLimit` (janela no `access_logs`).
- **Integração:** `login → needs_otp → verify-otp → sessão`; dispositivo confiável pula
  OTP; OTP errado/expirado; bloqueio por tentativas; revogação de dispositivo.
- **Mailer:** `ConsoleMailer` nos testes; asserção do código enviado.
- TDD: RED → GREEN → refactor.
