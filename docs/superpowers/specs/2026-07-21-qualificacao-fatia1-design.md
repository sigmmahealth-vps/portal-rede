# Qualificação — Fatia 1 (spec 5.4.1 / 5.4.2)

Data: 2026-07-21
Escopo: OPS-CTR-FOR-002 §§ 5.4.1.2 (fluxo), 5.4.2.1 (gestão de ciclos), 5.4.2.2 (status), 5.4.2.3 (classificação e DL).

## Contexto

A Fatia 0 (spec `2026-07-21-painel-auditor-543-design.md`) entregou o Painel do Auditor + CRUD manual de ciclos. Restam três lacunas centrais para o processo funcionar ponta a ponta:

1. **Modelo de ciclo** — hoje o ciclo é só uma janela temporal. A spec exige lista de grupos participantes com roteiro por grupo, unicidade por prestador/unidade e um mecanismo de abertura que crie as instâncias em massa.
2. **Fluxo por critério** — o `AuditorEvaluationModal` atual só marca não-conformidade + observação e recalcula tudo no cliente. A spec pede aprovar / reprovar / solicitar reanálise **por critério**, com histórico de iterações, e parecer final que calcula o selo no servidor.
3. **Classificação e DL** — as faixas exatas da spec (Ouro >90.00%, Prata >60.00%, Bronze ≤60.00%, sem eliminatório reprovado para Ouro/Prata), "Documento Legal" como parte da Segurança, e bypass automático quando o prestador já tem o documento válido em cadastro.

Esta spec cobre as três frentes juntas. A Fatia 2 (parecer/certificado/plano de ação) e Fatia 3 (acompanhamento trimestral + notificações) ficam de fora.

## Divergência conhecida do dado

`provider_group='RECURSO PRÓPRIO'` aparece com dois roteiros distintos em dev (FOR-004 e FOR-024). A modelagem "grupo → roteiro" da spec presume 1:1. O código lida com a exceção herdando `providers.eval_script_id` como base do `eval_cycle_groups`, mas o admin passa a poder ver/editar o mapping antes de abrir o ciclo — quem não coubesse no 1:1 fica listado no preview como "grupo sem roteiro mapeado" para desambiguação manual.

## Schema — Migration `0020_qualificacao_fatia1.sql`

```sql
-- 1. Vínculo grupo↔roteiro por ciclo (spec 5.4.2.1).
CREATE TABLE IF NOT EXISTS eval_cycle_groups (
  id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  cycle_id       bigint NOT NULL REFERENCES eval_cycles(id) ON DELETE CASCADE,
  provider_group text NOT NULL,
  script_id      bigint NOT NULL REFERENCES eval_scripts(id),
  UNIQUE (cycle_id, provider_group)
);
CREATE INDEX IF NOT EXISTS eval_cycle_groups_cycle_idx ON eval_cycle_groups (cycle_id);

-- 2. Unicidade (prestador, unidade) por ciclo (spec 5.4.2.1 regra de negócio).
CREATE UNIQUE INDEX IF NOT EXISTS eval_instances_cycle_puloc_uniq
  ON eval_instances (cycle_id, provider_id, COALESCE(location_id, 0));

-- 3. Coluna document_type para bypass DL (spec 5.4.2.3 observação).
ALTER TABLE eval_questions ADD COLUMN IF NOT EXISTS document_type text;
CREATE INDEX IF NOT EXISTS eval_questions_document_type_idx
  ON eval_questions (document_type) WHERE document_type IS NOT NULL;

-- 4. Histórico de iterações por critério (spec 5.4.1.2 etapa 4).
CREATE TABLE IF NOT EXISTS eval_answer_iterations (
  id                bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  answer_id         bigint NOT NULL REFERENCES eval_answers(id) ON DELETE CASCADE,
  iteration_number  int NOT NULL,
  actor_id          bigint REFERENCES users(id) ON DELETE SET NULL,
  actor_role        text NOT NULL CHECK (actor_role IN ('prestador','auditor')),
  action            text NOT NULL
                     CHECK (action IN ('respondeu','solicitou_reanalise','aprovou','reprovou')),
  answer_value      text,
  score_obtained    numeric(8,2),
  evidence_url      text,
  observation       text,
  created_at        timestamptz NOT NULL DEFAULT now(),
  UNIQUE (answer_id, iteration_number)
);
CREATE INDEX IF NOT EXISTS eval_answer_iterations_answer_idx
  ON eval_answer_iterations (answer_id);
```

`providers.eval_script_id` fica no schema como legado — a abertura do ciclo passa a consumir de `eval_cycle_groups`, mas o valor herdado do prestador é usado como palpite inicial para pré-popular `eval_cycle_groups` (ver Abertura, abaixo). Marca `ponytail:` no schema.

`evidence_status` em `eval_answers` já é `text` sem CHECK — passa a aceitar o novo valor `aguardando_reanalise` sem migration extra.

## Parser — extração de `document_type`

`db/roteiro-parser.ts` ganha uma função pura `extractDocumentType(text, guidance)` que retorna um label normalizado ou `null`. Regras (aplicadas em ordem, primeira match ganha):

| Padrão (case-insensitive, em `text` OU `guidance`) | Label |
|---|---|
| `alvará sanitário` | `Alvará Sanitário` |
| `alvará de funcionamento` | `Alvará de Funcionamento` |
| `corpo de bombeiros`, `AVCB`, `bombeiros` | `Alvará Corpo de Bombeiros` |
| `CNES`, `cadastro nacional (de )?estabelecimento` | `CNES` |
| `anotação de responsabilidade técnica`, `\bART\b` | `ART` |
| `PGRSS`, `resíduos de serviços de saúde` | `PGRSS` |
| `\bPGR\b` (não `PGRSS`) | `PGR` |
| `PCMSO`, `controle médico e saúde ocupacional` | `PCMSO` |
| `contrato social` | `Contrato Social` |
| `RQE`, `registro de qualificação de especialista` | `RQE` |

O extractor **só se aplica** quando `dimension='Documento Legal'` (S/C/E ficam sempre com `document_type=null`). Sem match → `null` (crítério DL sem bypass possível).

Reimport dos 15 roteiros existentes é idempotente (o import já faz upsert por `code + text`). Testes cobrem cada regra + os padrões negativos (PGR não bater com PGRSS, ART não bater com "ART cardíaca").

## Endpoints

Todos protegidos por `authenticate`. `isStaff` reutilizado.

### Abertura de ciclo

**`GET /api/eval/cycles/:id/abertura-preview`** — dry-run. Retorna:
```json
{
  "cycle": { "id": 1, "label": "Ciclo 2026" },
  "would_create": {
    "groups": 22,
    "instances": 740,
    "dl_bypass": 15
  },
  "excluded": {
    "providers_without_group": [{"id": 42, "name": "…"}],
    "providers_without_medical_guide": 0,
    "groups_without_script_mapping": ["RECURSO PRÓPRIO"]
  }
}
```
`groups_without_script_mapping` lista qualquer grupo cujo `providers.eval_script_id` divirja entre membros — precisa ser desambiguado antes.

**`POST /api/eval/cycles/:id/abrir`** — grava tudo em uma transação (`withTransaction`):
1. Guard: ciclo `active=true` E `NOT EXISTS(instances WHERE cycle_id=id)`.
2. Popula `eval_cycle_groups` a partir de `providers.provider_group + providers.eval_script_id` distinct — pula grupos ambíguos (que aparecem no preview como excluídos).
3. Para cada `provider_locations` com `in_medical_guide=true` cujo `provider.provider_group` está em `eval_cycle_groups`, cria 1 `eval_instances` com `status='pendente'`, `cycle_id`, `script_id` derivado do grupo.
4. **DL bypass em lote**: para cada instância criada, para cada `eval_questions.document_type IS NOT NULL` do roteiro, se existe documento válido do prestador (query abaixo), insere `eval_answers` com estado terminal aprovado + registra 1 iteration com `action='aprovou'`, `actor_role='auditor'`, `actor_id=NULL` (sistema).
   ```sql
   SELECT file_url FROM documents
    WHERE provider_id = $1 AND type = $2 AND status = 'valido'
      AND (expiry_date IS NULL OR expiry_date >= CURRENT_DATE)
    ORDER BY issue_date DESC NULLS LAST LIMIT 1
   ```
5. `auditLog` com `action='cycle_opened'`, meta = counts do preview.
6. Retorna o mesmo shape do preview + `created: {groups, instances, dl_bypass}`.

### Ações por critério (auditor)

Todas exigem `isStaff` e `eval_instances.status IN ('em_analise','aguardando_evidencia')`.

| Método | Rota | Body | Efeito |
|---|---|---|---|
| POST | `/api/eval/answers/:id/aprovar` | `{observation?}` | `evidence_status='aprovado'`, `auditor_observation` gravado, iteration `action='aprovou'`. |
| POST | `/api/eval/answers/:id/reprovar` | `{observation}` **obrigatória** | `evidence_status='reprovado'`, `score_obtained=0`, `is_non_compliant=true`, iteration `action='reprovou'`. |
| POST | `/api/eval/answers/:id/solicitar-reanalise` | `{observation}` **obrigatória** | `evidence_status='aguardando_reanalise'`, `auditor_observation` gravado, iteration `action='solicitou_reanalise'`. Se a instância estava em `em_analise`, transiciona para `aguardando_evidencia`. |

Todas gravam `iteration_number = MAX+1` para o `answer_id`. `auditLog` com `action='answer_<verbo>'` + meta `{instance_id, question_id, provider_id}`.

### Resposta do prestador (reanálise)

**`PUT /api/eval/answers/:id`** (extensão do endpoint existente `/instances/:id/answers` que já grava respostas em lote — passa a aceitar single-answer também):
- Guard: prestador dono da instância + `evidence_status IN ('pendente','aguardando_reanalise')`.
- Atualiza `eval_answers` (value, score, evidence_url).
- Reset `evidence_status='pendente'`.
- Registra iteration `action='respondeu'`, `actor_role='prestador'`.

O endpoint em lote atual segue funcionando para o preenchimento inicial (uma iteration por answer). Quando lote termina, cada answer nova/alterada gera **uma** iteration `respondeu`.

### Submeter para análise (prestador)

**`POST /api/eval/instances/:id/submit`**:
- Guard: prestador dono, status atual em `('em_andamento','aguardando_evidencia')`.
- Verifica **completude**: para cada `eval_questions` do roteiro, precisa existir uma `eval_answers` correspondente com `answer_value` não-vazio (`'sim'|'nao'|'NA'` ou valor de tipo texto/numérico quando aplicável). Faltando → 409 `{error, missing_question_ids:[…]}`.
- Se qualquer `evidence_status='aguardando_reanalise'` ainda existir, 409 `{error, pending_answer_ids:[…]}`.
- Muda status para `em_analise`. `completed_at` **não** muda aqui (só no parecer). `auditLog`.

### Parecer final (auditor)

**`POST /api/eval/instances/:id/parecer`**:
- Guard: `isStaff`, status = `em_analise`, TODAS as answers em estado terminal (`aprovado` ou `reprovado`) — se não, 409 `{error, pending:[…]}`.
- Recalcula server-side:
  ```
  score = SUM(score_obtained WHERE answer_value != 'NA')
  max_possible = SUM(max_score WHERE answer_value != 'NA')
  percentual = score / max_possible * 100  (0 se max_possible=0)
  hasEliminatoryFailed = EXISTS(answers WHERE evidence_status='reprovado' AND eval_questions.is_eliminatory=true)
  seal = computeSeal(percentual, hasEliminatoryFailed)
  ```
- Atualiza `status='aprovado'`, `completed_at=now()`, grava score/percentual/seal.
- Retorna `{status, percentual, seal, hasEliminatoryFailed}`.
- `auditLog` com `action='evaluation_finalized'`.

**`PUT /api/eval/instances/:id/status`** (legado): passa a ignorar `seal` do body (comentário `ponytail:`); mantém a rota até o `AuditorEvaluationModal` novo estar em produção.

## Helpers puros

### `src/lib/computeSeal.ts`
```ts
export function computeSeal(percentual: number, hasEliminatoryFailed: boolean): 'Ouro'|'Prata'|'Bronze' {
  if (hasEliminatoryFailed) return 'Bronze';
  if (percentual > 90.00) return 'Ouro';
  if (percentual > 60.00) return 'Prata';
  return 'Bronze';
}
```
Testes: bordas (90.00 → Prata; 90.01 → Ouro; 60.00 → Bronze; 60.01 → Prata; 100 → Ouro; 0 → Bronze); eliminatório reprovado com 95% → Bronze; eliminatório reprovado com 30% → Bronze.

**Decisão de interpretação**: a spec (5.4.2.3) diz "Ouro/Prata: sem critério eliminatório reprovado" mas não define o que fazer se `percentual > 60%` E há eliminatório reprovado. Escolha: **rebaixa a Bronze** — eliminatório reprovado é sinal negativo forte e deve rebaixar sempre. Se o produto quiser outra semântica (ex.: "não qualificado"), muda 1 linha do helper e o teste correspondente.

### `src/lib/dimensionAgg.ts`

export interface DimTotals { dimension: string; score: number; max_possible: number; }
export function mergeSecurityDL(rows: DimTotals[]): DimTotals[];
// Colapsa "Documento Legal" em "Segurança" (soma score e max_possible).

Usado por:

- Endpoint `/dashboard/auditor.xlsx` — mesmo agrupamento no SQL. Coluna "% Segurança" reflete a soma automaticamente. Coluna "% Doc. Legal" **não existe** (nunca esteve no export).

## Deferrals (`ponytail:`)

- Sem CHECK/enum em `documents.type` — continua text livre; UI de upload de documento (fora desta fatia) passa a sugerir os labels normalizados.
- Sem lock otimista (`updated_at`) em `eval_answers` — dois auditores editando o mesmo critério = último vence. Add when time > 1 auditor.
- Sem rollback de iteration (auditor não pode "desaprovar" — cria nova iteration).
- Sem paginação de critérios no modal do auditor (roteiros ~40-60 itens). Add when passar de 200.
- Prestador não vê contagem de rodadas de um critério, só a orientação atual.
- Sem exportação do histórico de iterações. Add when auditoria pedir.
- Sem revalidação automática do bypass DL ao subir/atualizar documento do prestador. Add when for pedido — hoje bypass roda só no momento da abertura do ciclo.
- Sem migration retroativa das 3 instâncias em dev que foram criadas antes do parecer (`status='pendente'` sem answers reais).
