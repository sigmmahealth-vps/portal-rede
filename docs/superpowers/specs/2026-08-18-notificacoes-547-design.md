# Notificações Automáticas — Qualificação e Plano de Ação (spec 5.4.7 / S5)

Data: 2026-08-18. Escopo: o bloco 5.4.7 da S5 (notificações) + provisionamento
manual de acesso do prestador (pré-requisito para as notificações chegarem a
alguém). Relatórios/exportações e publicação em produção ficam fora deste spec.

## Objetivo

Notificar prestador e auditoria nos 12 eventos da tabela 5.4.7, por dois canais:
**Portal** (sininho do header, hoje um mock hardcoded no `Layout.tsx`) e **E-mail**
(Resend, infra existente em `auth/mailer.ts`).

## Decisões de produto (fechadas com o usuário)

1. **Destinatário "Prestador"** = usuários ativos do portal vinculados ao
   `provider_id`. **Sem usuário → sem e-mail** (não há fallback para e-mail
   cadastral). O acesso do prestador é provisionado manualmente pelo admin
   (seção "Provisionamento de acesso"); o convite é o primeiro contato.
2. **Destinatário "Auditor"** = todos os usuários ativos com role `auditoria`
   (admin NÃO recebe).
3. **Eventos de prazo disparam uma única vez por item** (dedupe persistente); a
   notificação fica no portal até ser lida. Sem lembretes repetidos.
4. **Sininho real** + página `/notificacoes` ("Ver todas", paginada).
5. **Arquitetura A com outbox embutido**: sem fila/worker; a própria tabela
   `notifications` guarda o status do e-mail e o job horário existente re-tenta
   falhas (teto de 3 tentativas).
6. **Provisionamento de acesso do prestador é manual, por prestador**: o admin
   atualiza o cadastro e dispara o convite pela aba Gestão de Acessos. Nada de
   criação automática em massa nem na abertura do ciclo.
7. **Criação com senha manual continua existindo** (solicitação do cliente) ao
   lado do fluxo de convite.
8. **Modelo 1 usuário : 1 prestador mantido**, mas o provisionamento fica isolado
   numa função própria para não fechar a porta a um futuro 1:N (grupos que
   administram vários CNPJs — 60 e-mails cadastrais compartilhados hoje no dev).

## Dados — migration `0030_notifications.sql`

```sql
CREATE TABLE IF NOT EXISTS notifications (
  id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id        bigint REFERENCES users(id) ON DELETE CASCADE,  -- NULL = só e-mail (canal e-mail-apenas)
  email_to       text,             -- NULL = só portal (ex.: canal Portal-apenas)
  provider_id    bigint REFERENCES providers(id) ON DELETE CASCADE,
  type           text NOT NULL,
  title          text NOT NULL,
  body           text,
  link           text,             -- rota interna do portal
  dedupe_key     text UNIQUE,      -- só eventos de prazo; NULL nos transacionais
  read_at        timestamptz,
  email_status   text NOT NULL DEFAULT 'na'
                   CHECK (email_status IN ('na','pendente','enviado','falhou')),
  email_attempts int NOT NULL DEFAULT 0,
  created_at     timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ... ON notifications (user_id, read_at);        -- sininho/contagem
CREATE INDEX ... ON notifications (email_status)             -- varredura do retry
  WHERE email_status IN ('pendente','falhou');
```

- **Uma linha por destinatário.** Evento para 3 auditores = 3 linhas.
- `user_id` preenchido → aparece no sininho. `email_to` preenchido → vai por e-mail.
  Canal e-mail-apenas (ex.: `roteiro_pendente`) = linha com `email_to` preenchido
  e `user_id` NULL (nunca aparece no portal; existe para dedupe + outbox).
- Canal "só Portal" (ex.: submit → auditoria) = `email_status='na'`, `email_to` NULL.
- Outbox: `pendente`/`falhou` com `email_attempts < 3` é re-tentado pelo job horário.
  `falhou` com 3 tentativas é terminal (fica visível no portal mesmo assim, se tiver user).

## Eventos

### Transacionais — emitidos inline no ponto de código existente

| `type` | Gatilho | Destino | Canal |
|---|---|---|---|
| `ciclo_aberto` | `openCycleCore` cria as instâncias | Prestador | E-mail + Portal |
| `roteiro_enviado` | `POST /eval/instances/:id/submit` | Auditoria | Portal |
| `reanalise_solicitada` | `auditorAction('solicitou_reanalise')` **e** `POST /reopen` (devolução integral) | Prestador | E-mail + Portal |
| `parecer_aprovado` / `parecer_reprovado` | `POST /eval/instances/:id/parecer` | Prestador | E-mail + Portal |
| `certificado_emitido` | emissão do certificado dentro do parecer | Prestador | E-mail + Portal |
| `plano_gerado` | os 2 pontos que auditam `action_plan_generated` | Prestador + Auditoria | E-mail + Portal |
| `acao_aguardando_validacao` | item do plano → status `aguardando_revisao` | Auditoria | Portal |

Notas:
- "Abertura do ciclo" e "Roteiro disponível" acontecem no mesmo instante neste
  sistema (abrir ciclo = criar instâncias). Emitimos **uma** notificação combinada
  (`ciclo_aberto`: "Ciclo X aberto — seu roteiro está disponível"), não duas.
- Devolução integral (`/reopen`): 1 notificação por instância, não por critério.
- Reanálise por quesito: 1 notificação por ação do auditor (cada quesito devolvido
  gera a sua — é o comportamento natural do gatilho e dá rastreio por critério).

### De prazo — job horário, disparo único (dedupe)

| `type` | Condição (checada a cada hora) | `dedupe_key` | Destino | Canal |
|---|---|---|---|---|
| `acao_vencendo` | item não concluído/cancelado com `due_date - 15d ≤ hoje` | `acao_vencendo:item:<id>:<dest>` | Prestador | E-mail + Portal |
| `acao_atrasada` | item não concluído/cancelado com `due_date < hoje` | `acao_atrasada:item:<id>:<dest>` | Prestador + Auditoria | E-mail + Portal |
| `roteiro_pendente` | instância não enviada (status `pendente`/`em_andamento`) com `end_date - 30d ≤ hoje` no ciclo | `roteiro_pendente:inst:<id>:<dest>` | Prestador + Auditoria | **Só e-mail** (spec) |
| `certificado_vencendo` | certificado com `valid_until - 30d ≤ hoje` e `valid_until ≥ hoje` | `cert_vencendo:cert:<id>:<dest>` | Prestador | E-mail + Portal |

- Dedupe: `INSERT ... ON CONFLICT (dedupe_key) DO NOTHING`; e-mail só dispara se a
  linha foi inserida. Como o destinatário pode ser N usuários, a chave inclui o
  destinatário: `<type>:<ref>:<user_id|email>`.
- `roteiro_pendente` é só e-mail (canal da spec): grava a linha com `user_id` NULL
  e `email_to` = e-mail do usuário destinatário. A linha existe só para dedupe +
  outbox e nunca aparece no portal.
- `roteiro_pendente` para a **auditoria** é um **resumo por ciclo** ("N roteiros
  pendentes — ciclo X encerra em DD/MM"), dedupe `roteiro_pendente:cycle:<id>:<dest>`.
  Individual por instância seria ~600 e-mails por auditor. O prestador recebe o
  aviso individual da própria instância.

## Emissor — `src/lib/notify.ts` + wiring no `server.ts`

- **Catálogo por tipo** (função pura, testável): `renderNotification(type, ctx)` →
  `{ title, body, link, emailSubject, emailText }`. Texto puro no padrão do mailer
  atual. `ctx` carrega nomes/datas (provider_name, cycle_label, due_date...).
- **`notifyEvent(type, ctx, recipients)`** (server-side): recebe destinatários já
  resolvidos, insere as linhas e dispara os e-mails **fire-and-forget** (falha de
  e-mail vira `email_status='falhou'` + log; nunca quebra a request do evento).
- **Resolução de destinatários** (função com SQL): `prestadorRecipients(providerId)`
  → usuários ativos vinculados ao provider (vazio = ninguém recebe; sem fallback).
  `auditoriaRecipients()` → usuários ativos role `auditoria`.
- **Mailer:** novo método genérico `sendNotification(to, subject, text)` nas duas
  implementações (`ConsoleMailer`, `ResendMailer`). Nada de método por tipo.

## Job horário

Pega carona no `setInterval(runAutoCycleJobs, 1h)` existente — vira uma segunda
função no mesmo tick (`runNotificationJobs`), com try/catch próprio:

1. **Varredura de prazo:** roda as 4 queries de condição, monta destinatários e
   chama `notifyEvent` (o dedupe garante disparo único).
2. **Retry de e-mail:** `SELECT ... WHERE email_status IN ('pendente','falhou') AND
   email_attempts < 3 LIMIT 50` → re-envia, incrementa `email_attempts`, marca
   `enviado`/`falhou`.

Varredura primeiro, retry depois — assim um e-mail de prazo que falhe na 1ª
tentativa já é re-tentado no tick seguinte.

## Provisionamento de acesso do prestador (Gestão de Acessos)

Pré-requisito prático das notificações: sem usuário, prestador não recebe nada.
Hoje a aba exige e-mail + senha digitados na mão e não tem convite.

- **Pré-preenchimento:** `GET /providers/:id/access` passa a devolver
  `suggested_email` (primeiro e-mail válido de `provider_locations`) quando não
  existe usuário; a aba preenche o campo com ele (cobertura hoje no dev: 554/676).
- **Convite:** `POST /providers/:id/access` sem `password` cria o usuário sem
  senha utilizável e envia o convite com link de definição de senha (mesma
  mecânica de setup-token do staff, validade 24h). Botão principal da aba:
  "Criar acesso e enviar convite".
- **Senha manual mantida:** com `password` no body, comportamento atual (cliente
  pediu essa possibilidade).
- **Reenviar convite:** enquanto `invite_status = 'pending'`, a aba mostra
  "Reenviar convite" — reusa `POST /api/users/:id/resend-invite` já existente.
- **Alteração posterior:** e-mail editável na aba como hoje (fluxo de update
  existente); trocar e-mail com convite pendente reenvia o convite para o novo
  endereço.
- **Isolamento:** a lógica vira `provisionProviderAccess(providerId, {email,
  password?})` — chamadores não sabem se o modelo é 1:1; um futuro 1:N troca só
  essa função.
